Architecture Spec

Readworthy CLI

A two-phase CLI for auditing Markdown documentation ecosystems, estimating token savings, and converting selected docs to semantic HTML without breaking compatibility. Planned feature.

Status Design Decision Why CLI-first Commands Two-Phase Workflow Data Shapes Validation Rules Compatibility Error Handling Agent Usage Design Principles

Planned feature

The Readworthy CLI does not exist yet. This document is an architecture specification — and an example of what a technical spec looks like rendered with Readworthy. See the roadmap →

Design decision: Readworthy should be CLI-first with an optional agent skill layer. The CLI performs deterministic repo analysis, token auditing, validation, and conversion. The agent skill orchestrates the CLI conversationally — it does not contain transformation logic.

Why CLI-first

Need Best fit Reason
Repo scanning CLI Requires filesystem access, deterministic paths, and repeatable output across runs.
Token estimates CLI Requires consistent file-size and tokenizer heuristics that should not vary by model or session.
Markdown-to-HTML conversion CLI Transformations must be reproducible, testable, and reversible without model involvement.
Migration reasoning Agent skill Useful for explaining tradeoffs, answering questions, and generating user-facing recommendations.
Orchestration and approval flow Agent skill Natural language workflow — ask, review, approve, execute — is the agent's native mode.

The CLI is the engine. The skill is the interface. Transformation logic lives in the binary. The agent invokes the binary, interprets the output, and handles the human conversation.

Commands

Read-only

readworthy init

Audits the repository, identifies Markdown spec files, estimates context cost, classifies compatibility, and outputs a proposed migration plan to .readworthy/plan.json. Does not modify any files. Run this first.

Writes files

readworthy convert

Executes the approved plan. Creates HTML files, optionally converts Markdown loaders, backs up originals to .readworthy/backups/, validates output, and reports actual token savings.

Read-only

readworthy audit

Recalculates token and context estimates after changes. Use after editing generated HTML to verify the estimate is still accurate and the CSS is correctly excluded from the count.

Read-only

readworthy validate

Validates generated HTML files for structural correctness: one h1 per file, no duplicate IDs, no inline styles, readworthy.css linked as a render layer, CSS excluded from agent-context estimate.

Two-Phase Workflow

readworthy init

Validation Rules

Spec detection by name and classification

Recognize common Markdown spec names and classify them by compatibility requirement. Classification should be based on ecosystem role, not filename alone — a file named design.html.md should still be classified by its content type.

README.md, AGENTS.md, SKILL.md, install.md, design.md, brand.md, product.md, validation.md, components.md, prompts.md, workflows.md, architecture.md, CHANGELOG.md, CONTRIBUTING.md, LICENSE

Token estimates must be labeled

Every token count in CLI output must be labeled with ~ or the word "estimated" unless a real tokenizer was used. Do not present heuristic guesses as facts. When a tokenizer is available, label output as "exact."

CSS must not appear in agent-context estimates

When calculating token projections, exclude readworthy.css from the count in all scenarios. It is a render layer, not a context file. Including it inflates the "current load" estimate and misrepresents the actual agent context.

Loader files must not reference CSS

A generated .md loader file that references an HTML artifact must not include or imply that the agent should load readworthy.css. The CSS link belongs only in the HTML output file itself.

HTML output must have exactly one h1

Validate that each generated HTML file has precisely one h1 element. Multiple h1s indicate a structural generation error. Zero h1s indicate a missing document title.

No duplicate element IDs

Run an ID uniqueness check on each generated HTML file. Duplicate IDs break anchor navigation and violate the HTML spec. This is a validation failure, not a warning.

No inline styles in generated HTML

Generated HTML must not contain style="" attributes. All visual decisions belong in the readworthy.css token system or in a :root override block. Inline styles are a signal that the generation prompt was not following the Readworthy output spec.

readworthy.css linked, not inlined

The stylesheet must appear as a link tag in the document head, not as a style block with the full stylesheet content. Inlining the CSS defeats the purpose of a shared render layer and inflates file size.

Token estimation uses the Tiktoken library when available (Node 20+). On Node 16 or when Tiktoken is unavailable, the CLI falls back to a characters-divided-by-4 heuristic and labels all estimates with ~.

Error Handling

Unrecoverable errors exit non-zero

If the CLI encounters a file it cannot parse, a plan.json that references a file that no longer exists, or a backup directory that already contains a conflicting .bak file, it exits with a non-zero status code and does not proceed. Partial conversion is not attempted — review and fix the error, then re-run.

Exit code Condition Recovery
0 Success —
1 Plan file not found or malformed Run readworthy init to regenerate plan.json
2 Target file conflict — HTML already exists at conversion target Delete the existing file or update the plan target path
3 Backup conflict — .bak file already exists in backups/ Review the existing backup, move or delete it, then retry
4 Validation failure after conversion Review the failure report, fix the HTML, run readworthy validate
5 CSS inlining detected in generated output Regenerate the affected file with the correct output prompt

Agent Usage

When the user asks you to analyze or convert their documentation, run readworthy init first. Read the output carefully. Present the Planned Operations list to the user before proceeding — do not run readworthy convert without explicit user approval. If the user approves, run: readworthy convert --plan .readworthy/plan.json. After conversion, always run readworthy validate and report any failures before presenting the token savings summary. If validation fails, report the specific failure and ask the user whether to fix manually or regenerate the affected file.

Example invocation prompt

Run readworthy init on this repository and show me the proposed migration plan. Do not convert any files until I review and approve the plan. After I approve, run the conversion, then run validate and show me the results. If validation fails on any file, stop and report the specific failure before continuing.

Design Principles

Never overwrite without backup. The CLI must create a .bak file for every Markdown file it modifies, in the .readworthy/backups/ directory. Conversion is reversible by design.

Estimates are estimates. Every token count must be labeled with ~ or "estimated" unless a real tokenizer was used. Presenting heuristic guesses as facts erodes user trust and misrepresents the tool's capabilities.

The skill does not contain the CLI. The agent skill is a conversational interface. The transformation logic lives exclusively in the CLI binary. Skills that contain transformation code become brittle and drift from the tool's actual behavior.

Not: Markdown-to-HTML converter.
Better: AI documentation architecture optimizer — for structure, compatibility, and context efficiency.

CLI + Skill Relationship

CLI   = analysis engine, converter, validator, reporter
Skill = conversational interface, recommendation explainer, workflow orchestrator

The optional skill teaches the agent how to run readworthy init, interpret its plan, ask for approval at the right moment, and invoke readworthy convert. It does not duplicate the transformation logic. The two components communicate through the filesystem — plan.json, audit-report.json, and the conversion outputs.
