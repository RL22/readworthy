## Output format

When generating specs, summaries, research briefs, architecture references,
agent instructions, workflow guides, or any structured document longer than
~20 lines that will be shared with a team or read repeatedly:

Produce semantic HTML using Readworthy instead of Markdown.
Full reference: https://rl22.github.io/readworthy/examples/readworthy-skill.html

Works with any agent that reads a project config file — Claude Code (CLAUDE.md), Codex (AGENTS.md), Cursor, Windsurf, or any custom setup. The agent follows the URL when it needs the full component vocabulary.

First run — ask about design

Before generating output for the first time, ask the user one question: "Do you have a DESIGN.md I can apply, or should I use Readworthy's default styles?" If DESIGN.md exists: map its color, typography, and radius tokens to the --rw-* CSS variables in the Design Tokens section below. Add a <style> override block in <head> immediately after the stylesheet link. If no DESIGN.md: add one link tag and proceed. <link rel="stylesheet" href="readworthy.css">

Do not load readworthy.css as agent context

The stylesheet is a render artifact. Agents gain no reasoning benefit from it and burn significant context tokens. Link it in HTML output only — never paste it into a prompt or agent config file.

Output Structure

Every Readworthy document uses this shell. Do not omit body.doc, header.doc-hero, or main.prose. 

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>[Document Title]</title>
  <link rel="stylesheet" href="readworthy.css" />
</head>
<body class="doc">

<header class="doc-hero">
  <p class="eyebrow">[Document type — Spec · Summary · Brief · Reference]</p>
  <h1>[Title]</h1>
  <p class="lede">[One sentence: what this is and who it's for]</p>
</header>

<nav class="toc" aria-label="Table of contents">
  <a href="#section-id">Section Name</a>
</nav>

<main class="prose">

  <!-- Content sections -->

</main>

</body>
</html>

With DESIGN.md — token override

Add a <style> block immediately after the stylesheet link. All components inherit the variables automatically — no other changes needed. 

<link rel="stylesheet" href="readworthy.css">
<style>
  :root {
    --rw-bg:      [background from DESIGN.md];
    --rw-fg:      [foreground text from DESIGN.md];
    --rw-accent:  [primary accent color from DESIGN.md];
    --rw-font:    [body font stack from DESIGN.md];
    --rw-mono:    [monospace font stack from DESIGN.md];
    --rw-radius:  [border radius from DESIGN.md];
  }
</style>

Complete Component Library

Page structure

ClassElementUse for
body.doc<body>Document root. Required on every Readworthy page.
.doc-hero<header>Page hero. Contains eyebrow, h1, and lede.
.prose<main>Content container. Sets width constraint and vertical rhythm.
.toc<nav>Horizontal pill row for site nav or in-page anchor links.

Typography

ClassElementUse for
.eyebrow<p>Document type label above h1. Mono, accent color, uppercase.
.lede<p>Standfirst or subtitle beneath h1. Muted, slightly larger.
.principle<p>Key rule or guiding statement. Use <strong> for the label.

Callouts

ClassElementUse for
.note<aside>Supplemental context. Muted. Does not interrupt the primary read.
.callout<section>Featured statement. Slightly larger. TL;DR or key takeaways.
.warning<section>Risk, caveat, or blocker. Warning color. Must not be missed.

Content blocks

ClassElementUse for
.example<section>Code or output block with subtle frame. Add eyebrow to label it.
.spec-card<section>Structured unit with surface background. Badge + heading + body.
.validation-rule<section>Constraint or validation block. Same surface as spec-card.
.prompt-block<section>Prompt display. Contains an h3 label and a pre block.
.agent-instruction<section>Agent-facing instruction. Renders in monospace. Write in second person.
.timestamp<section>Timestamped entry. Contains a <time> and an h3.
.file-tree<pre>Directory or file tree. Dark background, mono, preserves whitespace.

Lists and labels

ClassElementUse for
.checklist<ul>Task or decision list. Items render with accent-colored checkmarks.
.compact-list<ul>Standard list with reduced padding. Pair with .checklist as needed.
.badge<span>Tag or label pill. Same style as .toc links. Place above card headings.

Layout and status

ClassElementUse for
.card-grid<section>Responsive auto-fit grid. Wraps spec-cards. Minimum 14rem per card.
.status-grid<section>Semantic alias for card-grid. Use for compatibility matrix layouts.
.status.supported<span>Passing, complete, supported. Accent-tinted background.
.status.partial<span>In progress, partial support. Muted background.
.status.neutral<span>Not applicable, not recommended. Muted background.
.status.required<span>Required, blocked, failing. Warning-tinted background.

When to Apply

If more answers are yes than no, produce Readworthy HTML. Otherwise keep Markdown.

  • Will the document exceed ~20 lines of structured content?
  • Does it contain multiple sections a reader needs to navigate?
  • Will it be shared with a team, stored as a reference, or read more than once?
  • Is it a spec, brief, operational artifact, or decision record?
  • Does the content benefit from cards, callouts, code blocks, or checklists?

Keep Markdown for

README.md, AGENTS.md, CLAUDE.md, SKILL.md, CHANGELOG.md, LICENSE, inline code comments, and any file an ecosystem discovers by exact filename. HTML does not satisfy those routing requirements.

Core model: Markdown routes. HTML operates. CSS renders.

Roadmap

The AGENTS.md pattern above is the current install method. Two additional distribution mechanisms are planned:

Planned

agentskills.io Skill

A proper readworthy/SKILL.md with YAML frontmatter, installable via the agentskills.io registry. Enables one-command install and automatic activation based on task type — no manual AGENTS.md edits required.

Planned

Readworthy CLI

readworthy init, convert, audit, and validate — for auditing Markdown ecosystems, estimating token savings, and converting docs without breaking compatibility. See the architecture spec →
