HTML Artifacts, Readability, and the HTML Tax

A research scan of emerging projects that turn AI output, terminal output, tool calls, and files into richer browser-based interfaces — plus the counterargument that storing HTML as source can increase token cost.

← Home Summary The Pattern HTML Tax
Research question: Is the industry moving from plain Markdown dumps toward rendered operational artifacts, and where does that create value versus token/context waste?

Executive Summary

The linked projects point to a clear pattern: AI output is increasingly being rendered as browser-native interfaces, not just Markdown in a terminal. The movement spans agent skills, CLIs, generative UI components, no-framework HTML systems, React/MDX renderers, and skill registries.

The screenshot included in the prompt highlights the strongest counterargument: HTML can cost substantially more tokens than equivalent Markdown when both store the same content. Its example frames this as “the HTML tax,” showing a 3KB Markdown file at 789 tokens versus the same content as HTML at 1,359 tokens, or 1.72× more.

Core constraint: The win is not “all HTML.” The win is using HTML where the output becomes more readable, interactive, actionable, or visual — while keeping Markdown or lightweight source formats for LLM-native storage, routing, and compatibility.

Project Notes

Agent Skill

visual-explainer

visual-explainer — visual-explainer describes itself as an agent skill that turns complex terminal output into styled HTML pages. Its README frames use cases like system architecture explanation, diff review, plan review, diagrams, data tables, and project recaps. This validates the readability thesis: replace low-bandwidth terminal output with visual explanations that are easier to scan, inspect, and share.

Anything to HTML

html-anything

html-anything — html-anything is a Codex / Claude Code skill that turns an idea, file, folder, or URL into a polished live HTML page. It can process exports like Amazon orders, WhatsApp chats, CSVs, transcripts, repos, folders of notes, and more. Its automatic style selection treats styles as design systems and layout systems, not superficial CSS skins.

Component Substrate

shadcn-html

shadcn-html — shadcn-html positions itself as the AI prototyping substrate: themeable, semantic HTML, modern CSS, and vanilla JavaScript built on shadcn/ui tokens with no framework, build step, npm install, or abstraction layers. Its component skills document markup, variants, ARIA, and wiring conventions.

Browser Render Layer

smithers-webui

smithers-webui — smithers-webui lets agents render React + MDX in a browser window for plans, diffs, decisions, dashboards, and other moments where Markdown in a terminal becomes lossy. Its ephemeral MDX-to-browser approach is important because rendered UI can be useful without becoming stored source bloat.

Generative UI

assistant-ui/tool-ui

assistant-ui/tool-ui — assistant-ui/tool-ui addresses raw model tool payloads. Instead of dumping JSON into conversation, it turns payloads into interactive UI such as approvals, forms, tables, charts, and media cards so users can understand and act without leaving the chat.

Skill Distribution

Happycapy-skills

Happycapy-skills — Happycapy-skills is a curated collection of production-ready skills for coding, design, documents, media, research, and automation. It matters as ecosystem evidence: skills are becoming packaging and distribution infrastructure for repeatable agent workflows.

The HTML Tax Counterargument

The screenshot argues that HTML can be expensive when stored as source. Its example compares the same content in Markdown and HTML, showing HTML at 1,359 tokens versus Markdown at 789 tokens. The artifact attributes the increase to tags, attributes, and class names fragmenting into more tokens.

FormatExample token countInterpretation
Markdown789 tokensLower token cost for equivalent source content.
HTML1,359 tokensHigher token cost when the same text is stored with tags/classes.
Difference1.72×HTML markup can be real context overhead if loaded by the model.
Research implication: HTML should not be treated as the default LLM-native storage format. It is more defensible as a render target, user-facing artifact, or selectively loaded operational view.

What These Projects Suggest

Confirmed

Readable artifacts are a real category

Multiple projects converge on browser-rendered outputs for plans, diffs, dashboards, diagrams, chats, and tool payloads.

Confirmed

Tension

The HTML tax screenshot makes the key distinction: HTML is valuable for humans, but not always optimal for repeated model reads.

Strategic Takeaways

  1. Do not frame this as Markdown versus HTML. The stronger framing is source versus artifact.
  2. Emphasize first-run value. A system should audit where HTML will help, where it will waste context, and where Markdown should remain untouched.
  3. Make generated HTML purposeful. HTML should create cards, comparisons, dashboards, evidence panels, filters, or decisions — not just wrap Markdown paragraphs.
  4. Keep CSS out of model context. The visual system matters for humans but should not be repeatedly loaded into the agent unless styling is the task.
  5. Prefer ephemeral or generated-on-demand views. smithers-webui’s ephemeral MDX-to-browser approach is a strong pattern for avoiding stored HTML bloat.
  6. Support compatibility layers. GitHub, skills, Codex, and many repo workflows still expect Markdown files such as README.md, AGENTS.md, and SKILL.md.

Recommended Positioning

Best synthesis: HTML is not the new source format for everything. HTML is the new interface layer for AI-generated artifacts that need to be read, reviewed, compared, or acted on.
Markdown = lightweight source, routing, compatibility
HTML     = human-facing artifact, operational view, interface
CSS      = presentation system, not default model context
Skills   = distribution layer for repeatable artifact workflows
